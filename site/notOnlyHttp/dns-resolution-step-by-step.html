How DNS Resolution Works, Step by Step With dig

By Boris Fain · Updated September 28, 2026

Most web requests start with a name lookup. Your browser sends a query to a recursive resolver (usually your ISP), which then chases a chain of authority: root nameserver, top-level domain (TLD) server, and finally the authoritative nameserver. Understanding how DNS resolution works step by step is essential if you debug network issues, build a service mesh, or simply want to know what happens before that HTTP request leaves your machine. This article walks through a real lookup using dig, then shows you how to write a minimal Go resolver that speaks DNS over UDP directly.

The Four Types of DNS Servers

DNS has a recursive, distributed architecture. When you type a domain into your browser, four different servers may be involved, each playing a different role:

  1. Recursive resolver: Your ISP or a public service (8.8.8.8, 1.1.1.1) that you query first. It does the work of chasing down the answer.
  2. Root nameserver: Tells the resolver which TLD server to contact. There are 13 root servers globally, identified by letters A through M.
  3. TLD nameserver: Handles all domains under a suffix (.com, .org, .net, etc.). Tells the resolver which authoritative server holds the actual record.
  4. Authoritative nameserver: The server operated by (or on behalf of) the domain owner. It has the actual DNS records for that domain.

Most end-users never interact directly with root or TLD servers. Your resolver does that automatically. But using dig with the +trace option, you can watch the entire chain unfold.

Breaking this down:

  • First block: Root nameservers (the starting point). Your recursive resolver already knows these from its local configuration.
  • Second block: After querying a root server, it responds with the .com TLD nameservers.
  • Third block: After querying a .com TLD server, it responds with the authoritative nameservers for example.com.
  • Fourth block: The final answer: example.com has an A record pointing to 93.184.216.34.

Notice the TTL (time-to-live) values: 518400 for root (6 days), 172800 for TLD (2 days), 3600 for the A record (1 hour). Each record can be cached independently. Your resolver caches answers to avoid repeating the full chain on the next lookup.

How the Query Protocol Works

DNS queries happen over UDP port 53 (or TCP 53 for large responses). The protocol is simple binary format defined in RFC 1035. A typical query includes:

  • Transaction ID (2 bytes, helps match responses to queries)
  • Flags (1 byte for question vs. response, recursion desired, etc.)
  • Question count, answer count, authority count, additional count (2 bytes each)
  • Questions (domain name, query type like A or MX, query class like IN for Internet)
  • Answer records (if response)
  • Authority records (if response)
  • Additional records (glue records, optimization)

Let's write a minimal Go program that builds a DNS query, sends it to a resolver, and parses the response by hand. This is what dig does internally, but we will do it from scratch: 

package main

import (
	"encoding/binary"
	"fmt"
	"net"
	"strings"
)

// DNS Header format (12 bytes)
type DNSHeader struct {
	ID      uint16
	Flags   uint16
	QDCount uint16 // Questions
	ANCount uint16 // Answers
	NSCount uint16 // Nameservers
	ARCount uint16 // Additional records
}

// Encode a domain name into DNS wire format (labels with length prefix)
// example.com becomes \x07example\x03com\x00
func encodeName(name string) []byte {
	parts := strings.Split(strings.TrimSuffix(name, "."), ".")
	result := []byte{}
	for _, part := range parts {
		result = append(result, byte(len(part)))
		result = append(result, []byte(part)...)
	}
	result = append(result, 0) // Root label
	return result
}

// Decode a domain name from DNS wire format
func decodeName(data []byte, offset int) (string, int) {
	parts := []string{}
	ptr := offset
	for {
		if ptr >= len(data) {
			break
		}
		len := int(data[ptr])
		if len == 0 {
			ptr++
			break
		}
		// Handle pointer compression (high 2 bits set to 11)
		if (len & 0xc0) == 0xc0 {
			// This is a pointer; for simplicity we skip full handling
			// A real implementation would jump and decompress
			ptr += 2
			break
		}
		ptr++
		parts = append(parts, string(data[ptr:ptr+len]))
		ptr += len
	}
	return strings.Join(parts, "."), ptr
}

func main() {
	// Create a DNS query for example.com A record
	header := DNSHeader{
		ID:      1234,           // Random transaction ID
		Flags:   0x0100,         // Standard query, recursion desired
		QDCount: 1,
		ANCount: 0,
		NSCount: 0,
		ARCount: 0,
	}

	// Encode the question
	query := []byte{}

	// Encode header (binary, big-endian)
	buf := make([]byte, 12)
	binary.BigEndian.PutUint16(buf[0:2], header.ID)
	binary.BigEndian.PutUint16(buf[2:4], header.Flags)
	binary.BigEndian.PutUint16(buf[4:6], header.QDCount)
	binary.BigEndian.PutUint16(buf[6:8], header.ANCount)
	binary.BigEndian.PutUint16(buf[8:10], header.NSCount)
	binary.BigEndian.PutUint16(buf[10:12], header.ARCount)
	query = append(query, buf...)

	// Encode the question section
	query = append(query, encodeName("example.com")...)
	query = append(query, 0x00, 0x01) // Type A (1)
	query = append(query, 0x00, 0x01) // Class IN (1)

	// Send query to 8.8.8.8:53 (Google Public DNS)
	conn, err := net.Dial("udp", "8.8.8.8:53")
	if err != nil {
		fmt.Printf("Error: %v\n", err)
		return
	}
	defer conn.Close()

	_, err = conn.Write(query)
	if err != nil {
		fmt.Printf("Error writing query: %v\n", err)
		return
	}

	// Read response (UDP max ~512 bytes without EDNS0)
	response := make([]byte, 512)
	n, err := conn.Read(response)
	if err != nil {
		fmt.Printf("Error reading response: %v\n", err)
		return
	}

	response = response[:n]

	// Parse response header
	respHeader := DNSHeader{
		ID:      binary.BigEndian.Uint16(response[0:2]),
		Flags:   binary.BigEndian.Uint16(response[2:4]),
		QDCount: binary.BigEndian.Uint16(response[4:6]),
		ANCount: binary.BigEndian.Uint16(response[6:8]),
		NSCount: binary.BigEndian.Uint16(response[8:10]),
		ARCount: binary.BigEndian.Uint16(response[10:12]),
	}

	fmt.Printf("Response ID: %d\n", respHeader.ID)
	fmt.Printf("Answer count: %d\n", respHeader.ANCount)

	// Skip question section (we know it's example.com A IN)
	offset := 12
	offset += len(encodeName("example.com")) + 4

	// Parse answer section
	for i := 0; i < int(respHeader.ANCount); i++ {
		name, newOffset := decodeName(response, offset)
		offset = newOffset

		recordType := binary.BigEndian.Uint16(response[offset : offset+2])
		offset += 2
		recordClass := binary.BigEndian.Uint16(response[offset : offset+2])
		offset += 2
		ttl := binary.BigEndian.Uint32(response[offset : offset+4])
		offset += 4
		rdlen := binary.BigEndian.Uint16(response[offset : offset+2])
		offset += 2

		fmt.Printf("\nName: %s\n", name)
		fmt.Printf("Type: %d (1=A, 5=CNAME, 15=MX, etc.)\n", recordType)
		fmt.Printf("Class: %d (1=IN)\n", recordClass)
		fmt.Printf("TTL: %d seconds\n", ttl)

		if recordType == 1 { // A record
			ip := net.IPv4(response[offset], response[offset+1], response[offset+2], response[offset+3])
			fmt.Printf("IP Address: %s\n", ip.String())
		}
		offset += int(rdlen)
	}
}

Run this with Go 1.19+: 

go run dns_query.go

Output:

Answer count: 1

Name: example.com.
Type: 1 (1=A, 5=CNAME, 15=MX, etc.)
Class: 1 (IN)
TTL: 3600 seconds
IP Address: 93.184.216.34

This program does what your resolver does millions of times per day. It crafts a binary DNS query, sends it over UDP, and parses the binary response. Notice that we bypass the full resolver chain here and ask Google's resolver directly (8.8.8.8), which already has the answer cached. If we queried a root server, we would get a referral instead of an answer.

Caching and TTL

DNS answers are cached at multiple levels:

Layer Duration Controlled by
Your system (OS resolver stub) Usually 0-600 seconds OS config, often no caching
Recursive resolver (ISP or public) Up to the TTL in the record Domain owner (SOA and record TTLs)
Browser cache Usually 1-30 minutes Browser settings
Root and TLD server responses 172800 seconds (2 days) IANA and registry

The TTL field in a DNS response tells caches how many seconds they may use the answer before re-querying. A low TTL (300-600 seconds) is useful during migrations. A high TTL (86400+ seconds) reduces load on authoritative servers but makes updates slower to propagate.

Query Types Beyond A Records

DNS is not just for IP lookups. Common record types:

  • A: IPv4 address.
  • AAAA: IPv6 address.
  • CNAME: Alias to another domain. Resolvers follow the chain automatically.
  • MX: Mail exchanger. Includes a priority number (lower is preferred).
  • TXT: Arbitrary text. Used for SPF, DKIM, DMARC, Let's Encrypt challenges, and service discovery.
  • NS: Nameserver delegation. Tells which server is authoritative for a zone.
  • SOA: Start of Authority. Contains zone metadata and serial number (used in zone transfers).
  • SRV: Service records. Specify host and port for a service (like _ldap._tcp.example.com).

Try these with dig: 

dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com TXT
dig @a.iana-servers.net example.com any

The last command queries the authoritative server directly (a.iana-servers.net) instead of your default resolver.

CNAME Chains and Redirect Loops

A CNAME points a domain to another domain name. Resolvers automatically follow the chain. For example: 

dig www.example.com

might return: 

www.example.com. 300 IN CNAME cdn.example.net.
cdn.example.net. 60 IN A 203.0.113.1

The resolver follows the CNAME and returns the final A record. If www.example.com points to www.example.com (or a cycle exists), the resolver will hit a maximum chain depth and fail. Most resolvers stop after 32 hops.

Common Mistakes

Mistake 1: Assuming dig queries your local resolver. By default, dig queries the resolver configured in /etc/resolv.conf (on Linux) or your system's DNS settings. Use dig @8.8.8.8 to override. Use dig +trace to see the full chain, not just one resolver's cached answer.

Mistake 2: Forgetting that UDP is connectionless. A DNS query over UDP can be lost or arrive out of order. Resolvers retransmit after 2-5 seconds and may try multiple servers if one does not respond. TCP is used for zone transfers and responses larger than 512 bytes.

Mistake 3: Confusing CNAME with A record redirection. A CNAME is a DNS-level alias. An HTTP redirect (301/302) is application-level. A CNAME saves one DNS lookup; a redirect forces the browser to make a second HTTP request.

Mistake 4: Not understanding TTL expiry. If you change a DNS record and set TTL to 86400 (1 day), old caches may still serve the old answer for up to a day. Lower the TTL before a migration, wait for it to expire, then change the record, then raise the TTL again after propagation.

Mistake 5: Blocking port 53 at the edge. If your firewall blocks outbound UDP 53, your machine cannot do DNS lookups. Some networks force all DNS through a local resolver. If you cannot reach external resolvers, check your firewall and routing.

DNS and Performance

A typical recursive lookup takes 50-300 milliseconds end to end. The biggest delays come from:

  • Network latency to the resolver (usually fast if local).
  • The resolver's cache miss (forces it to chain through root and TLD).
  • Authoritative server response time.
  • Slow CNAME chains.

For latency-sensitive services, use a local caching resolver (systemd-resolved on Linux, mDNSResponder on macOS, or a dedicated resolver like Unbound or PowerDNS Recursor). Pre-resolve frequently-used domains in your application startup.

Measure your own DNS latency with dig: 

dig example.com | grep "Query time"

Repeat it to see the difference between a cache miss (first query) and a cache hit (second query, much faster).

Debugging Tools Beyond dig

nslookup: Older, simpler than dig. Less flexible but useful for quick checks. 

nslookup example.com 8.8.8.8

host: Minimal DNS client. Good for scripts. 

host -t MX example.com

getent: Queries the system's name resolution library (NSS), which may use /etc/hosts, LDAP, or DNS. 

getent hosts example.com

strace: Trace system calls to see how a program does DNS. Useful if you want to know whether your app is using the system resolver or a custom one. 

strace -e openat,connect -f curl https://example.com 2>&1 | grep -E "resolv|53"

tcpdump: Capture DNS traffic on the wire. See exactly what queries and responses are sent. 

sudo tcpdump -i any -n "port 53"

DNS over HTTPS (DoH) and DNS over TLS (DoT)

Standard DNS over UDP 53 is unencrypted. An ISP or network observer can see every domain you visit. DoH (RFC 8484) wraps DNS queries in HTTPS requests. DoT (RFC 7858) uses TLS on port 853. Both are encrypted and privacy-preserving. Browsers like Firefox and Brave support DoH by default. Resolvers like Cloudflare (1.1.1.1) and Quad9 (9.9.9.9) support both.

In practice, if you control the server-side (not the end-user client), you may not care about DoH. But if you are building a mobile app or client software, consider supporting DoH for privacy.

FAQ

What happens if the root server is down?

If one root server is down, others are still reachable. There are 13 root server addresses (a-m), and each is actually a cluster of geographically distributed machines. Your resolver has backups. Root outages are rare and mitigated by this redundancy. However, if all root servers were down and no resolver had a cached answer, new domain lookups would fail.

How does reverse DNS work?

Reverse DNS (rDNS) maps an IP address back to a hostname. It uses a special zone: in-addr.arpa for IPv4. For example, 93.184.216.34 becomes 34.216.184.93.in-addr.arpa. A PTR record in that zone contains the hostname. Use dig -x 93.184.216.34 to query. Reverse DNS is optional and often missing. Email servers use it to fight spam.

Can I query DNS without a recursive resolver?

Yes, but it requires following the chain yourself. You query a root server, get a referral to a TLD server, query the TLD, get a referral to the authoritative server, query that, and get the answer. This is what dig +trace does. In practice, using a recursive resolver (8.8.8.8, 1.1.1.1) is simpler and faster due to caching.

What is DNSSEC?

DNSSEC (DNS Security Extensions, RFC 4033) adds cryptographic signatures to DNS responses. Each zone is signed with a private key. Validators check the signature using the zone's public key. This prevents DNS spoofing (where an attacker intercepts a query and returns a fake IP). DNSSEC is complex to deploy and not widely used yet, but major registries and cloud providers support it. Use dig +dnssec to see RRSIG records.

Why does DNS sometimes return multiple A records?

Round-robin load balancing. If example.com resolves to 10 different IP addresses, the authoritative server rotates through them, returning a different order each query. The client then picks the first one (or the resolver caches all and picks one at random). This spreads traffic across multiple servers. It is not as sophisticated as modern load balancing (which measures server health), but it is simple and works.

What is glue record?

A glue record is an A record for a nameserver returned in the additional section of a DNS response. Example: the .com TLD server responds with a.gtld-servers.net (NS record) and the IP address of a.gtld-servers.net (glue A record) in the same response. Without glue, the resolver would need another DNS lookup to learn the IP of the nameserver, creating a dependency loop. Glue records break the loop.

Is DNS used only for HTTP?

No. DNS is used by any service that needs to find a host by name. Email (SMTP, IMAP), file transfer (as documented in FTP specifications), SSH, VoIP, and most internet protocols rely on DNS. Even lower-level services like NTP and SNMP often use hostnames that must be resolved first.

Can I run my own authoritative nameserver?

Yes. You can run bind9, Knot, or PowerDNS on a dedicated server and point your domain's registrar to it. You must configure at least two nameservers for redundancy. You sign a zone file with your nameserver software, update your domain's glue records at the registrar, and manage zone updates (adding/removing records). Many hosting providers do this for you, but self-hosting is possible if you understand DNS and have reliable infrastructure.
