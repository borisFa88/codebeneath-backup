How to Handle Multiple Content Types in Spring Boot

Written by

Boris Fain

in

Spring Framework

A Spring Boot endpoint sometimes needs to accept more than one request format. A client might send JSON metadata, a binary payload, or a multipart file upload to the same path. Spring can select the correct controller method from the request's Content-Type header, so the application does not need one large method that parses every format manually.

Use one handler for each content type

Give each method the same path and a different consumes value. Spring performs content negotiation before calling the controller and returns 415 Unsupported Media Type when no handler accepts the request format.

package com.example.web;

import java.io.IOException;

import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestPart;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.multipart.MultipartFile;

@RestController
@RequestMapping("/api")
public class ContentController {

    @PostMapping(
            path = "/process",
            consumes = MediaType.APPLICATION_JSON_VALUE,
            produces = MediaType.TEXT_PLAIN_VALUE)
    public ResponseEntity<String> processJson(@RequestBody MyDto body) {
        return ResponseEntity.ok("JSON processed for " + body.name());
    }

    @PostMapping(
            path = "/process",
            consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE,
            produces = MediaType.TEXT_PLAIN_VALUE)
    public ResponseEntity<String> processBinary(@RequestBody byte[] body) {
        return ResponseEntity.ok("Binary payload: " + body.length + " bytes");
    }

    @PostMapping(
            path = "/process",
            consumes = MediaType.MULTIPART_FORM_DATA_VALUE,
            produces = MediaType.TEXT_PLAIN_VALUE)
    public ResponseEntity<String> processMultipart(
            @RequestPart("file") MultipartFile file) throws IOException {
        return ResponseEntity.ok(
                "Uploaded " + file.getOriginalFilename() + ": " + file.getSize() + " bytes");
    }

    public record MyDto(String name, int age) {}
}

Test each request with curl

Send JSON

curl -i -X POST http://localhost:8080/api/process \
  -H "Content-Type: application/json" \
  --data '{"name":"Boris","age":30}'

Expected response body: JSON processed for Boris.

Send a binary file

curl -i -X POST http://localhost:8080/api/process \
  -H "Content-Type: application/octet-stream" \
  --data-binary @sample.bin

Spring passes the exact request body to the byte[] parameter.

Upload a multipart file

curl -i -X POST http://localhost:8080/api/process \
  -F "[email protected]"

curl -F creates the multipart boundary and the correct content type automatically.

Do not use the Host header as the client identity

The HTTP Host header identifies the destination website. It does not identify the visitor, and a client can often choose its value. Never use it for authentication, authorization, rate-limit identity, or IP allowlists.

request.getRemoteAddr() returns the immediate network peer. When Cloudflare proxies a request, that peer is normally a Cloudflare address rather than the visitor's address. request.getRemoteHost() may perform a reverse DNS lookup and does not solve this problem.

Read the visitor IP safely behind Cloudflare

Cloudflare sends the original visitor address in CF-Connecting-IP. Trust this header only when the origin firewall accepts web traffic exclusively from Cloudflare IP ranges. Otherwise, an attacker can connect directly and supply a fake header.

private String clientIp(HttpServletRequest request) {
    String cloudflareIp = request.getHeader("CF-Connecting-IP");
    if (cloudflareIp != null && !cloudflareIp.isBlank()) {
        return cloudflareIp.trim();
    }
    return request.getRemoteAddr();
}

For production systems, configure the trusted-proxy layer centrally and validate addresses before storing or using them. Content-Type versus Accept: 415 and 406

Content-Type describes the request body; Accept describes response formats the client accepts. A consumes mismatch can produce 415. A produces mismatch with Accept can produce 406. Malformed JSON is a separate issue and commonly produces 400.

These handlers return plain text: use Accept: text/plain. For multipart uploads, let curl generate the boundary. The controller belongs in a Spring MVC application whose component scanning covers com.example.web. Its record example requires Java 17 or later. Create the sample files before running upload commands.
