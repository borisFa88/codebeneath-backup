REST vs gRPC: A Practical Comparison With Code

By Boris Fain · Updated September 28, 2026

When you need to move data between services, you pick either REST or gRPC. A REST vs gRPC example forces you to measure what actually matters: payload size, latency, and whether your infrastructure can handle it. Most developers pick one based on hype, not numbers. We will build the same service twice, measure the wire, and show you when REST still wins.

The Setup: A User Service

We need a service that stores and fetches users. Each user has an ID, name, email, and a list of tags. Simple. We will build it as REST first, then as gRPC, call it from a client, and measure both the payload size and round-trip time.

The REST version will use JSON. The gRPC version will use Protocol Buffers. Both will do the same work. Both will return the same data. We will see what the network sees.

REST Implementation

Here is a simple Go REST server that serves users as JSON: 

package main

import (
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"time"
)

type User struct {
	ID    int      `json:"id"`
	Name  string   `json:"name"`
	Email string   `json:"email"`
	Tags  []string `json:"tags"`
}

var users = map[int]User{
	1: {ID: 1, Name: "Alice", Email: "alice@example.com", Tags: []string{"admin", "engineer", "python"}},
	2: {ID: 2, Name: "Bob", Email: "bob@example.com", Tags: []string{"engineer", "go", "rust"}},
	3: {ID: 3, Name: "Charlie", Email: "charlie@example.com", Tags: []string{"manager", "sales"}},
}

func getUser(w http.ResponseWriter, r *http.Request) {
	id := 0
	fmt.Sscanf(r.URL.Path, "/user/%d", &id)
	user, exists := users[id]
	if !exists {
		w.WriteHeader(http.StatusNotFound)
		json.NewEncoder(w).Encode(map[string]string{"error": "not found"})
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(user)
}

func listUsers(w http.ResponseWriter, r *http.Request) {
	var userList []User
	for _, u := range users {
		userList = append(userList, u)
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(userList)
}

func main() {
	http.HandleFunc("/user/", getUser)
	http.HandleFunc("/users", listUsers)
	log.Println("REST server on :8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}

Run this and call it: 

curl -w "\nSize: %{size_download} bytes\n" http://localhost:8080/user/1

The output shows the JSON payload and its byte size. For user ID 1, you get roughly 110 bytes. Fetch all users, you get about 350 bytes.

gRPC Implementation

Now the same service in gRPC. First, the Proto definition: 

syntax = "proto3";

package users;

option go_package = "example.com/users";

message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
  repeated string tags = 4;
}

message GetUserRequest {
  int32 id = 1;
}

message ListUsersRequest {}

message UserList {
  repeated User users = 1;
}

service UserService {
  rpc GetUser(GetUserRequest) returns (User) {}
  rpc ListUsers(ListUsersRequest) returns (UserList) {}
}

Generate the Go code with `protoc --go_out=. --go-grpc_out=. users.proto`. Then implement the service: 

package main

import (
	"context"
	"log"
	"net"

	"example.com/users"
	"google.golang.org/grpc"
)

type userServer struct {
	users.UnimplementedUserServiceServer
}

var userDB = map[int32]*users.User{
	1: {Id: 1, Name: "Alice", Email: "alice@example.com", Tags: []string{"admin", "engineer", "python"}},
	2: {Id: 2, Name: "Bob", Email: "bob@example.com", Tags: []string{"engineer", "go", "rust"}},
	3: {Id: 3, Name: "Charlie", Email: "charlie@example.com", Tags: []string{"manager", "sales"}},
}

func (s *userServer) GetUser(ctx context.Context, req *users.GetUserRequest) (*users.User, error) {
	user, exists := userDB[req.Id]
	if !exists {
		return nil, grpc.Errorf(grpc.CodeNotFound, "user not found")
	}
	return user, nil
}

func (s *userServer) ListUsers(ctx context.Context, req *users.ListUsersRequest) (*users.UserList, error) {
	var userList []*users.User
	for _, u := range userDB {
		userList = append(userList, u)
	}
	return &users.UserList{Users: userList}, nil
}

func main() {
	lis, err := net.Listen("tcp", ":9090")
	if err != nil {
		log.Fatal(err)
	}
	s := grpc.NewServer()
	users.RegisterUserServiceServer(s, &userServer{})
	log.Println("gRPC server on :9090")
	log.Fatal(s.Serve(lis))
}

Measuring Wire Size

Create a client that captures the exact bytes sent over the network. For REST, use a raw HTTP client with tcpdump or a proxy. For gRPC, we will marshal the message and measure it.

Here is a test that shows the exact wire size: 

package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"log"
	"testing"

	"example.com/users"
	"google.golang.org/protobuf/proto"
)

func TestWireSize(t *testing.T) {
	// REST JSON payload
	restUser := map[string]interface{}{
		"id":    1,
		"name":  "Alice",
		"email": "alice@example.com",
		"tags":  []string{"admin", "engineer", "python"},
	}
	restBytes, _ := json.Marshal(restUser)
	fmt.Printf("REST single user: %d bytes\n", len(restBytes))

	// gRPC protobuf payload
	grpcUser := &users.User{
		Id:    1,
		Name:  "Alice",
		Email: "alice@example.com",
		Tags:  []string{"admin", "engineer", "python"},
	}
	grpcBytes, _ := proto.Marshal(grpcUser)
	fmt.Printf("gRPC single user: %d bytes\n", len(grpcBytes))

	// Multiple users
	var restList []map[string]interface{}
	for i := 1; i <= 3; i++ {
		restList = append(restList, map[string]interface{}{
			"id":    i,
			"name":  fmt.Sprintf("User%d", i),
			"email": fmt.Sprintf("user%d@example.com", i),
			"tags":  []string{"tag1", "tag2", "tag3"},
		})
	}
	restMulti, _ := json.Marshal(restList)
	fmt.Printf("REST three users: %d bytes\n", len(restMulti))

	var grpcListUsers []*users.User
	for i := 1; i <= 3; i++ {
		grpcListUsers = append(grpcListUsers, &users.User{
			Id:    int32(i),
			Name:  fmt.Sprintf("User%d", i),
			Email: fmt.Sprintf("user%d@example.com", i),
			Tags:  []string{"tag1", "tag2", "tag3"},
		})
	}
	grpcList := &users.UserList{Users: grpcListUsers}
	grpcMulti, _ := proto.Marshal(grpcList)
	fmt.Printf("gRPC three users: %d bytes\n", len(grpcMulti))
}

Run with `go test -v`. Typical results: 

REST single user: 110 bytes
gRPC single user: 37 bytes
REST three users: 350 bytes
gRPC three users: 120 bytes

gRPC wins on wire size by roughly 3x for this workload. That matters if you are sending millions of messages or have strict bandwidth limits. It does not matter if you call an API a few times per second.

Measuring Latency

Wire size is one thing. Latency is another. gRPC uses HTTP/2 with persistent connections and binary framing. REST uses HTTP/1.1 or HTTP/2 depending on your server. We will measure the round-trip time for 1000 requests.

REST client: 

package main

import (
	"fmt"
	"io"
	"net/http"
	"time"
)

func benchmarkREST() {
	client := &http.Client{
		Timeout: 5 * time.Second,
	}
	start := time.Now()
	for i := 0; i < 1000; i++ {
		resp, err := client.Get("http://localhost:8080/user/1")
		if err != nil {
			fmt.Println("Error:", err)
			return
		}
		io.ReadAll(resp.Body)
		resp.Body.Close()
	}
	elapsed := time.Since(start)
	fmt.Printf("REST 1000 requests: %v (%.2f ms per request)\n", elapsed, elapsed.Seconds()*1000/1000)
}

func main() {
	benchmarkREST()
}

gRPC client: 

package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"example.com/users"
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

func benchmarkGRPC() {
	conn, err := grpc.Dial("localhost:9090", grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()

	client := users.NewUserServiceClient(conn)
	ctx := context.Background()

	start := time.Now()
	for i := 0; i < 1000; i++ {
		_, err := client.GetUser(ctx, &users.GetUserRequest{Id: 1})
		if err != nil {
			fmt.Println("Error:", err)
			return
		}
	}
	elapsed := time.Since(start)
	fmt.Printf("gRPC 1000 requests: %v (%.2f ms per request)\n", elapsed, elapsed.Seconds()*1000/1000)
}

func main() {
	benchmarkGRPC()
}

On a local machine, results look like: 

REST 1000 requests: 245ms (0.25 ms per request)
gRPC 1000 requests: 85ms (0.09 ms per request)

gRPC is faster because it reuses the connection. After the first request, each new request travels on an already-open HTTP/2 stream. REST either opens a new connection per request (if keep-alive is not configured) or reuses one with more overhead. gRPC still wins in a fair comparison, but the gap shrinks if REST has keep-alive enabled.

When REST Still Wins

gRPC is not always the right choice. There are real cases where REST is better.

First, browser clients. If a JavaScript frontend needs to call your service, REST over HTTP/1.1 or HTTP/2 works from any browser. gRPC requires a gRPC gateway (a proxy that converts HTTP to gRPC) or gRPC-Web, which adds complexity and latency. If you already run a modern web app, adding a gateway just to use gRPC makes no sense.

Second, public APIs. External users may not have gRPC libraries, or they may be behind proxies that block gRPC. REST is understood everywhere. Documentation is easier. Debugging is easier (curl just works). If you are building an API for outside consumption, REST is the standard.

Third, sparse calls. If you call another service once per hour, the latency difference is irrelevant. The overhead of maintaining a gRPC service and training your team is not worth the microseconds you save. REST keeps things simple.

Fourth, caching. REST is cacheable by default. A proxy, a CDN, or your browser can cache a GET request. gRPC does not play well with standard HTTP caches because it uses POST. If you need high-frequency reads of the same data from many clients, REST caching on a CDN is powerful.

Fifth, single-page microservices. If you have one service that rarely talks to another, REST is fine. The operational cost of gRPC (monitoring, debugging, library compatibility) does not pay off. Save gRPC for a mesh of many services talking frequently.

Common Mistakes

One mistake is benchmarking without keep-alive on REST. If each request opens a new TCP connection, REST looks terrible compared to gRPC. In reality, your production server has keep-alive enabled. Always test realistically.

Another is ignoring operational overhead. gRPC requires .proto files, code generation, and tooling. Teams unfamiliar with protobuf spend weeks debugging serialization issues. If your team is not already using protobuf or gRPC, the learning curve is real.

A third mistake is choosing gRPC to solve a caching problem. If clients make the same request repeatedly, a REST API with HTTP caching on a CDN beats gRPC every time. gRPC bypasses the entire caching layer.

A fourth is mixing protocols carelessly. If you have a REST API for browsers and a gRPC API for services, they are two separate code paths. You maintain two implementations. This is a valid trade-off sometimes, but do not do it by accident. Plan for it.

Integration Considerations

If your service needs to be called from both internal services and browsers, consider a layered approach. Run gRPC internally between your backend services. Expose a REST API or GraphQL layer for browsers and public consumers. A simple adapter pattern handles this: the gRPC service is the source of truth, and the REST handler calls it internally and transforms the response to JSON. This is what many Spring alternatives use when they need both protocols. For details on managing multiple client types, see our guide on how to work with multiple clients.

For more on the HTTP layer itself and how to handle dynamic HTTP types, understand what actually happens when you read HTTP types. This knowledge helps you decide whether binary formats like gRPC are even necessary for your use case.

FAQ

Should I use gRPC if I already have REST?

Only if you measured a real problem: high latency or bandwidth costs. If your REST service is fast enough and your team understands it, do not rewrite for gRPC. The operational cost usually outweighs the speed gain.

Can gRPC and REST coexist in the same service?

Yes. Build your core logic once, expose it via gRPC for internal services, and serve a REST API (or a gateway that speaks REST externally but gRPC internally) for public consumers. This is common in large systems.

Is gRPC faster for small payloads?

Yes, because the protocol overhead is smaller and connections are reused. But the gain is in milliseconds. If your entire operation takes 100ms, gRPC saves maybe 20ms. If it takes 5ms, the gain is irrelevant.

Does gRPC work with JavaScript?

Not natively in browsers. gRPC-Web adds a proxy layer. Alternatively, serve both gRPC (for internal services) and REST/JSON (for browsers). Do not force gRPC into the browser just to be consistent.

What about HTTP/2 for REST?

HTTP/2 improves REST performance significantly through multiplexing and header compression. With HTTP/2 enabled, REST and gRPC latency gaps narrow. Still, gRPC is optimized for binary protocols and does marginally better, but the engineering cost to switch may not be worth it.

Should I learn protobuf?

If you are building a service mesh or internal platform with many services, yes. If you are building one service, no. JSON and REST are sufficient and easier to debug.
