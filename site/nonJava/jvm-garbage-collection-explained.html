JVM Garbage Collection Explained: G1, ZGC and When to Tune

By Boris Fain · Updated September 30, 2026

JVM garbage collection explained comes down to this: the garbage collector finds objects your code no longer uses and reclaims their memory. What makes it complicated is that stopping your application threads to do that work creates latency spikes, and different collectors make different tradeoffs between pause time, throughput, and memory overhead. You can run Java without ever touching a GC flag and be fine for many workloads. But if you ship user-facing code that stalls during garbage collection, or you build backend services that need predictable latency, you need to understand what the collector is actually doing and how to read its logs.

Three Collectors: Serial, G1, and ZGC

The JVM gives you three production-grade collectors. SerialGC is the baseline: single-threaded, simple, compact. It pauses the entire application to collect. Use it for small, latency-insensitive services and development. G1 (Garbage First) is the default in Java 9 and later: it divides the heap into regions, collects the "garbage first" (young generation, then oldest dirty regions), and uses multiple threads. It was built for heaps from a few hundred MB to tens of GB. ZGC is the newcomer: it scavenges the heap in parallel with your application using colored pointers and load barriers, achieving microsecond pause times even on multi-terabyte heaps. It costs throughput.

Which one you choose depends on your constraints. If you have a 2 GB microservice and 100 ms pauses are fine, G1 is reasonable. If you have a 10 GB cache server and every millisecond of pause means dropped requests, ZGC is worth the 3-5% throughput hit. If you have a batch job with 8 GB heap and no users waiting, SerialGC finishes faster.

How SerialGC Works (The Baseline)

SerialGC stops your entire application, walks the object graph starting from stack roots, marks live objects, sweeps dead ones, and compacts the heap. It does this in two phases: young generation (frequent, fast) and full collection (rare, slow). You run it with -XX:+UseSerialGC.

Here is a simple allocation program that will trigger garbage collection: 

import java.util.*;

public class AllocHeavy {
    static class Obj {
        byte[] data = new byte[1024];
        String name;
        
        Obj(String name) {
            this.name = name;
        }
    }
    
    public static void main(String[] args) {
        List<Obj> tenured = new ArrayList<>();
        
        for (int i = 0; i < 100_000; i++) {
            List<Obj> young = new ArrayList<>();
            for (int j = 0; j < 100; j++) {
                young.add(new Obj("young_" + j));
            }
            
            // Every 10 iterations, keep half the young set alive.
            if (i % 10 == 0) {
                tenured.addAll(young.subList(0, 50));
            }
            
            // Simulate work.
            long sum = 0;
            for (int k = 0; k < young.size(); k++) {
                sum += young.get(k).name.length();
            }
            System.out.println("Iteration " + i + ", sum=" + sum);
        }
        
        System.out.println("Tenured size: " + tenured.size());
    }
}

Compile and run with SerialGC and verbose GC logging: 

javac AllocHeavy.java
java -XX:+UseSerialGC \
  -Xmx512m \
  -Xms512m \
  -Xlog:gc*:file=serial.log:time,level,tags:uptime AllocHeavy 2>&1 | head -50

The log will show young generation collections (marked "Pause Young") with pauses in the 10-100 ms range. Every few seconds, if the tenured space gets full, you see a "Pause Full" that stops everything for 500+ ms on this heap size.

G1GC: The Workhorse

G1 divides the heap into 2 MB regions. Each region is either young, old, or free. When collecting, G1 picks the regions with the most garbage (hence "Garbage First") and evacuates the live objects into other regions. It does this in parallel using multiple threads.

Run the same program with G1: 

java -XX:+UseG1GC \
  -Xmx512m \
  -Xms512m \
  -XX:MaxGCPauseMillis=200 \
  -Xlog:gc*:file=g1.log:time,level,tags:uptime AllocHeavy 2>&1 | head -50

G1 tries to keep pauses under your target (200 ms here). You will see "Pause Young (Normal)" entries in the 50-150 ms range and far fewer full collections. The log shows both the pause time and the amount of memory freed.

Reading a Real GC Log: Line by Line

Here is an example G1 log entry (actual output from the above run): 

[2025-01-15T10:23:45.123+0000][2100ms][gc] GC(5) Pause Young (Normal) (G1 Evacuation Pause)
[2025-01-15T10:23:45.156+0000][2133ms][gc] GC(5) 256M->145M(512M) 33.123ms

What this tells you: at time 2100 ms of runtime, collection #5 started. It was a young generation pause. It paused for 33.123 milliseconds. The heap shrank from 256 MB to 145 MB of actual usage (the heap size is fixed at 512 MB). That 33 ms pause is the user-facing latency spike. If your service is supposed to respond to requests in under 10 ms, this collection paused you for three request windows.

A full collection log line looks different: 

[2025-01-15T10:23:52.300+0000][9300ms][gc] GC(18) Pause Full (System.gc())
[2025-01-15T10:23:52.800+0000][9800ms][gc] GC(18) 480M->210M(512M) 500.001ms

Full pause, 500 ms. If the old generation fills up and G1 cannot recover space fast enough, it falls back to serial full GC. This is the scenario you design to avoid.

ZGC: Microsecond Pauses at a Cost

ZGC (Zero GC) was introduced in Java 11 and is production-ready in Java 15 and later. It runs concurrent marking and relocation alongside your application. Instead of moving objects and updating pointers the old way, ZGC uses "colored pointers": bits in the pointer itself encode the object's marking state. When your code reads a pointer, a "load barrier" inline checks the color and does any necessary work (like moving the object) before the load completes. This allows ZGC to compact the heap without stopping your threads.

Run the same allocation test with ZGC: 

java -XX:+UseZGC \
  -Xmx512m \
  -Xms512m \
  -Xlog:gc*:file=zgc.log:time,level,tags:uptime AllocHeavy 2>&1 | head -50

ZGC log output is different. You will see "GC(x) Major" and "GC(x) Minor" without the "Pause" keyword most of the time. The pauses that do occur are marked in microseconds or single-digit milliseconds. Collect the logs from all three runs and compare: 

echo "=== SerialGC pauses ===" && \
grep "Pause" serial.log | awk '{print $NF}' | sort -n | tail -5

echo "=== G1GC pauses ===" && \
grep "Pause" g1.log | awk '{print $NF}' | sort -n | tail -5

echo "=== ZGC pauses ===" && \
grep "Pause" zgc.log | awk '{print $NF}' | sort -n | tail -5

On typical hardware, SerialGC's tail pauses will be 200-600 ms. G1's will be 50-200 ms. ZGC's will be under 10 ms, often under 1 ms, even for full heap traversals.

Pause Time vs. Throughput Tradeoff

The colored pointer and load barrier strategy ZGC uses adds CPU overhead. Every read of an object reference runs a load barrier check. This means ZGC typically delivers 3-5% lower peak throughput than G1. For a batch job that runs once a night, that matters. For a user-facing API that must not stall, the tradeoff is worth it. G1 sits in the middle: reasonable pauses (tens of ms) with minimal throughput loss.

Collector Max Pause Time Heap Size Throughput Cost
SerialGC 500+ ms Up to 2 GB None (single-threaded baseline)
G1GC 50-200 ms (tunable) 1-40 GB 5-10%
ZGC < 10 ms (typical) 4 GB to 16 TB 3-5%

Tuning and When You Should (and Should Not)

Most JVM applications run fine with no explicit GC tuning. The ergonomics (automatic tuning) in modern Java choose heap size based on available cores and RAM. If you have 16 cores and 32 GB available, the JVM will claim 1/4 of RAM by default (8 GB) and use G1.

Tune when you measure a problem. Use JFR (Java Flight Recorder) to record a 60-second window: 

java -XX:StartFlightRecording=duration=60s,filename=profile.jfr,settings=profile AllocHeavy
jfr print profile.jfr | grep -i "gc pause"

If you see pauses over your SLA (Service Level Agreement), then:

1. For G1, lower -XX:MaxGCPauseMillis (e.g., to 100 instead of 200). This collects more frequently but keeps pauses shorter.

2. If you cannot afford pauses above 5 ms, switch to ZGC. Verify the memory overhead (ZGC uses roughly 2% more heap for internal tracking) is acceptable.

3. If your heap is under 2 GB and you have no latency pressure, SerialGC gives you the fastest wall-clock time.

Do not tune based on hearsay. Do not add "-XX:+AggressiveHeap" or obscure flags because a blog post from 2008 said to. Most such flags are either broken or make things worse for your specific case.

Common Mistakes

Mistake 1: Disabling garbage collection. Some developers think they can call System.gc() explicitly and avoid the JVM's automatic collection. This does not work reliably and usually makes things worse by triggering full GC cycles at the worst times. Let the collector do its job.

Mistake 2: Setting heap size too high. A 64 GB heap sounds like more is better, but larger heaps mean longer pause times for full collections. If G1 has to scan 64 GB to find garbage, that pause will be seconds. Heap size should be just large enough that you are not hitting full GC in production. Aim for young generation collections every 1-2 seconds.

Mistake 3: Ignoring allocation rate. A program that allocates 100 MB per second will trigger young GC every few seconds regardless of which collector you use. If the allocation rate is the bottleneck, no collector tuning will help. You need to reduce allocations: use object pools, reuse arrays, or switch to lower-level languages if the cost is critical. (See native-language.html for when that trade-off makes sense.)

Mistake 4: Comparing pause times without methodology. One developer says "ZGC is 10x faster" based on a single log line. Pause time depends on heap usage, allocation rate, number of cores, and the CPU itself. Always collect 10+ minutes of logs and look at the 99th percentile, not the minimum.

FAQ

Should I use ZGC in production right now?

Yes, if you are on Java 15 or later and your pause times matter. ZGC was marked production-ready in Java 17. The only gotcha is that it does not support the compact object header optimization yet, so memory overhead is 1-3% higher than G1. If your heap is memory-constrained, test both.

What is the difference between young and old generation collection?

Young generation collection (minor GC) sweeps objects in the young space, which fill up fast because most objects die young. Old generation (major GC) collects longer-lived objects. Young collections are frequent and fast. Old collections are rare but slow, because more objects survive and need relocation. G1 tries to collect young more often and old only when necessary. ZGC collects both concurrently.

How do I know if my application is GC-bound?

Run jstat or JFR. If GC time is above 5% of wall-clock time, you are spending too much effort on collection. Either increase heap, reduce allocations, or pick a lower-pause collector. If GC time is under 2%, you are fine.

Can I use G1 and ZGC together?

No. You choose one collector per JVM invocation. The flag -XX:+UseG1GC or -XX:+UseZGC is mutually exclusive.

What about Java's newer collectors like Shenandoah?

Shenandoah is similar to ZGC, used mainly in Red Hat environments. G1 and ZGC cover almost all use cases. Shenandoah is included in OpenJDK but less battle-tested in large-scale production than ZGC.

Is GC performance the same in different Java implementations?

No. OpenJDK/HotSpot (standard Java) and GraalVM have G1 and ZGC. Eclipse Temurin, Amazon Corretto, and Azul are OpenJDK forks with the same collectors. Older commercial JDKs had custom collectors. Stick with OpenJDK 17 or later unless you have a specific vendor lock-in reason.
