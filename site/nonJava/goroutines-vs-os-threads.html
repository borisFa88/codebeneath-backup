Goroutines vs OS Threads: What Runs Where

By Boris Fain · Updated September 28, 2026

When you write concurrent code, the runtime either maps your tasks directly to operating system threads or manages them internally. This difference between goroutines vs threads example is foundational: a Java program that tries to spawn 10,000 threads will crash or hang, but an equivalent Go program will run smoothly. Understanding what actually runs where, and why, lets you write scalable systems instead of bumping into hard resource walls.

The Problem: OS Threads Are Expensive

Operating system threads are kernel objects. When you create one, the kernel allocates a stack (usually 1-8 MB), a thread-local storage block, context-switch data structures, and registers it in a global thread table. There are only so many before the kernel refuses to create more, and each one consumes real memory even when idle. On a typical Linux machine, you might spawn 10,000 threads before running out of memory or hitting a system limit.

Both Java and C++ (via std::thread) are bound by this constraint because they run one language-level thread per OS thread. If you create a Java Thread object, it becomes a kernel thread. If you spawn 100,000 Java threads, the JVM attempts to reserve 100,000 kernel threads, and your machine melts.

Go takes a different approach. Goroutines are lightweight user-space tasks managed entirely by the Go runtime. You can spawn millions of them on a single machine. The runtime multiplexes them onto a small pool of OS threads using a scheduler.

How Goroutines Work: M, P, N

The Go runtime scheduler uses three layers:

  • M (Machine): An OS thread managed by the Go runtime. Usually one per CPU core, plus a few for blocking I/O.
  • P (Processor): A logical processor, tied to a CPU core. Contains a queue of runnable goroutines.
  • G (Goroutine): A user-space task with a small stack (starting at 2 KB, growing as needed).

When you call go func(), the runtime adds a new goroutine to a work queue. The scheduler picks an idle OS thread (M) and a processor (P), then runs goroutines from that P's queue until they block. When a goroutine performs I/O or synchronous system calls, the M can yield and run another G, or the scheduler creates a new M to prevent other goroutines from starving. This is preemptive scheduling: the runtime can pause a goroutine and switch to another without waiting for it to call a function or yield explicitly.

Runnable Comparison: Go vs Java

Let's measure. Here is a Go program that spawns 100,000 goroutines, runs them, and prints memory used. 

package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	var m runtime.MemStats

	fmt.Println("=== Go Goroutines ===")

	runtime.ReadMemStats(&m)
	fmt.Printf("Memory before: %v MB\n", m.Alloc/1024/1024)

	var wg sync.WaitGroup
	start := time.Now()

	for i := 0; i < 100000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			time.Sleep(100 * time.Millisecond)
		}()
	}

	wg.Wait()
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m)
	fmt.Printf("Memory after: %v MB\n", m.Alloc/1024/1024)
	fmt.Printf("Time: %v\n", elapsed)
	fmt.Printf("Total goroutines: %v\n", runtime.NumGoroutine())
}

Running this on a modern Linux machine with 4 CPU cores: 

=== Go Goroutines ===
Memory before: 0 MB
Memory after: 21 MB
Time: 101ms
Total goroutines: 1

100,000 goroutines, 21 MB total, all done in about 100 ms. The scheduler multiplexed them onto a handful of OS threads.

Now, the same attempt in Java: 

import java.lang.management.ManagementFactory;
import java.lang.management.MemoryMXBean;

public class ThreadBurst {
    public static void main(String[] args) throws InterruptedException {
        MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();

        System.out.println("=== Java Threads ===");
        System.out.println("Memory before: " + 
            (memoryBean.getHeapMemoryUsage().getUsed() / 1024 / 1024) + " MB");

        Thread[] threads = new Thread[100000];
        long start = System.currentTimeMillis();

        try {
            for (int i = 0; i < 100000; i++) {
                final int id = i;
                threads[i] = new Thread(() -> {
                    try {
                        Thread.sleep(100);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
                threads[i].start();
            }

            for (Thread t : threads) {
                if (t != null) t.join();
            }
        } catch (OutOfMemoryError e) {
            System.out.println("OutOfMemoryError: " + e.getMessage());
        } catch (Exception e) {
            System.out.println("Error: " + e.getClass().getName() + ": " + e.getMessage());
        }

        long elapsed = System.currentTimeMillis() - start;
        System.out.println("Memory after: " + 
            (memoryBean.getHeapMemoryUsage().getUsed() / 1024 / 1024) + " MB");
        System.out.println("Time: " + elapsed + " ms");
    }
}

Compiling and running with default JVM settings: 

javac ThreadBurst.java
java ThreadBurst

Output (typical): 

=== Java Threads ===
Memory before: 45 MB
Error: java.lang.OutOfMemoryError: unable to create new native thread

The JVM tries to allocate a 1 MB stack per thread (default on many systems) and hits the limit. You can tweak this with -Xss to use smaller stacks, but you still bottleneck on file descriptor limits, kernel thread tables, and memory. Most JVMs max out around 10,000 to 32,000 threads depending on OS and configuration.

Why Go Goroutines Are Lighter

Goroutines start with a 2 KB stack and grow dynamically. They do not call into the kernel to be created. The runtime allocates them on the heap, so spawning one costs a small allocation and pointer bookkeeping. Context switching between goroutines happens in user space, not in the kernel, so it is orders of magnitude faster than OS thread switching.

Java Thread objects map directly to kernel threads. The JVM calls pthread_create (on Linux) or equivalent, which is a system call. This is expensive and limited by kernel tuning.

A comparison table:

Aspect Go Goroutine Java Thread C++ std::thread
Managed by Go runtime (user space) JVM + OS kernel OS kernel only
Stack size 2 KB initial, grows 1-8 MB fixed 1-8 MB fixed
Creation cost Heap allocation System call System call
Context switch User space, fast Kernel, slow Kernel, slow
Max on typical machine Millions 10K-32K 10K-32K

When Blocking Matters

Here is the deeper win for Go. When you spawn 1,000 goroutines that all call time.Sleep() or wait on network I/O, the Go scheduler detects this. If a goroutine blocks on a system call that the runtime does not intercept, the runtime detects that the M (OS thread) is stuck and spins up a new M to run other goroutines. If the goroutine blocks on a channel or other Go construct, the scheduler just parks it and runs the next goroutine from the queue on the same M. Either way, other work continues.

In Java, if a thread blocks, that OS thread is stuck. If you have 10,000 threads waiting on network calls, your CPU is underutilized because each OS thread is holding a kernel resource. You must explicitly manage this with thread pools and async patterns (Future, CompletableFuture, virtual threads in Java 21+). See our article on Go language fundamentals for more on why this design scales.

Java Virtual Threads: A Recent Exception

Java 21 introduced virtual threads (Project Loom), which work similarly to goroutines: they are light user-space tasks managed by the JVM scheduler, not OS threads. A virtual thread can block without blocking an OS thread. This brings Java much closer to Go's scalability model. However, virtual threads are still newer and require Java 21+. Most production systems still use platform threads (the traditional Thread class tied to OS threads).

Scheduling and Fairness

The Go scheduler is fair. It uses a work-stealing queue: each P has a local queue of runnable goroutines, and the scheduler periodically checks a global queue to prevent starvation. If all goroutines are CPU-bound (no blocking), the scheduler distributes them evenly across P's, and each P's M runs goroutines in round-robin fashion.

However, the Go scheduler is not preemptive in the traditional sense for CPU-bound loops. If a goroutine never blocks and never calls a function that yields, it can starve others. Go 1.14 introduced async preemption to fix this: the runtime injects preemption points. In practice, this rarely causes issues because most goroutines either block or call library functions frequently.

Java's thread scheduler is preemptive at the OS level. The kernel time-slices threads, so fairness is guaranteed by the OS. This is simpler but more expensive because every slice requires a context switch into the kernel.

Common Mistakes

Mistake 1: Assuming goroutines run in parallel. Goroutines are concurrent, not necessarily parallel. If you have one CPU core and 1,000 goroutines, only one runs at a time. They are scheduled fairly, but only one executes instructions per moment. Parallelism requires multiple cores. Run runtime.NumCPU() to check available parallelism.

Mistake 2: Not closing channels or not signaling completion. If a goroutine waits on a channel that is never sent to, it leaks. Use sync.WaitGroup or context cancellation to ensure all goroutines exit cleanly.

Mistake 3: Sharing mutable state without synchronization. Goroutines are lightweight, but Go is not magic. If two goroutines write to the same variable, you must protect it with a mutex or use channels to pass ownership. Race detectors exist for this: run tests with go test -race.

Mistake 4: Creating unbounded goroutine pools. It is easy to spawn a goroutine for each request in a web server. If requests come faster than goroutines complete, you leak memory and slow down. Use a worker pool or semaphore pattern to limit concurrency.

Measuring Real Impact

Here is a more realistic example: a simple HTTP server that spawns a goroutine per request, with a 50 ms I/O delay. 

package main

import (
	"fmt"
	"io"
	"net/http"
	"runtime"
	"time"
)

func handler(w http.ResponseWriter, r *http.Request) {
	time.Sleep(50 * time.Millisecond)
	io.WriteString(w, "OK\n")
}

func main() {
	go func() {
		for {
			time.Sleep(1 * time.Second)
			var m runtime.MemStats
			runtime.ReadMemStats(&m)
			fmt.Printf("Goroutines: %d, Heap: %d MB\n",
				runtime.NumGoroutine(),
				m.Alloc/1024/1024)
		}
	}()

	http.HandleFunc("/", handler)
	fmt.Println("Server on :8080")
	http.ListenAndServe(":8080", nil)
}

Start this server and hammer it with concurrent requests: 

go run server.go &
ab -n 10000 -c 1000 http://localhost:8080/

The server spawns a goroutine per request, so under heavy load you might see 1,000 concurrent goroutines and heap usage around 50-100 MB. A Java servlet container doing the same thing with one thread per request would struggle or run out of memory.

FAQ

Can I tune Java to spawn more threads?

Partially. You can reduce thread stack size with -Xss256k or similar, and increase file descriptors and process limits at the OS level. But you are fighting OS design. A typical tuned JVM might reach 50,000 threads instead of 10,000. Go routinely handles millions. Virtual threads in Java 21+ are a proper solution to this.

Do goroutines replace thread pools?

Not entirely. Goroutines let you spawn many lightweight tasks, but you still need to bound concurrency in some cases. An unbounded goroutine spawner under high load will exhaust memory. Use a semaphore or worker pool pattern to limit how many goroutines perform expensive work simultaneously.

How does Go handle blocking system calls?

The Go runtime wraps most blocking calls (like file I/O and network I/O) so the scheduler can park a goroutine without blocking the OS thread. For calls it cannot wrap (like certain C libraries), it detects the block and creates a new OS thread so other goroutines are not starved.

Is context switching between goroutines free?

No, but it is cheap. Switching happens in user space with no kernel call, no cache flush, and no register save. A goroutine switch is orders of magnitude faster than a kernel thread context switch. However, switching many goroutines on a single core still has overhead. For CPU-bound work, parallelism (multiple cores) matters more than concurrency (many goroutines on one core).

Why does Go use multiple OS threads if goroutines are so cheap?

True parallelism requires multiple cores, which requires multiple OS threads. A single OS thread can only run on one CPU core. The Go runtime creates one P (logical processor) per CPU core and one M per P, so you get parallelism. Extra M's are created for blocking I/O to prevent starvation.

Can C++ programs spawn goroutine-like tasks?

std::thread is tied to OS threads, so no. Some C++ libraries (like Boost.Fibers or Seastar) provide user-space task scheduling, but this is not in the standard library. For large-scale concurrency in C++, you typically use async I/O patterns or external libraries. See our piece on low-level concurrency patterns for comparison.
